# Протокол синхронизации заметок

Один протокол используется для всех хранилищ (S3, Яндекс Диск, Google Drive, собственный API).
Для хранилища это просто набор JSON-файлов, а вся логика слияния выполняется на клиенте.

## 1. Модель данных

Данные разбиты на **файлы по дням**, плюс отдельный файл для тегов:

| Файл                    | Содержимое                                                 |
|-------------------------|------------------------------------------------------------|
| `day-YYYY-MM-DD.json`   | заметки, созданные в этот день (локальная дата устройства) |
| `tags.json`             | справочник тегов                                           |

Почему именно так:
- Заметки почти всегда создаются «сегодня», поэтому разные устройства пишут в один файл только когда работают в тот же день. Архив прошлых дней не переписывается.
- Файлы получаются маленькими, и синхронизация передаёт только изменившиеся дни.
- В режиме «Регистрация» и в S3 с условной записью гонок нет совсем. На Диске и в Drive окно гонки сжимается до одного маленького файла.

Формат файла (каноничная сериализация: ключи отсортированы, записи отсортированы по `id`):

```json
{"records":[{"createdAt":1718000000000,"day":"2024-06-10","id":"…uuid…","tags":["работа"],"text":"Позвонить Ивану","updatedAt":1718000000000}],"v":1}
```

Запись заметки: `id` (UUID), `text`, `tags` (массив id тегов), `day`, `createdAt`, `updatedAt` (мс, Unix).
Запись тега: `id` (имя в нижнем регистре), `name`, `updatedAt`.
Удаление записывается как надгробие (tombstone): `{"id":"…","day":"…","deleted":true,"updatedAt":…}`.

### Версия формата

- `v` — версия формата файла (`FILE_FORMAT_VERSION`, сейчас `1`). Файл без `v` считается `v1`.
- Клиент, встретив файл с `v` больше своего, **не читает и не перезаписывает** его
  (`FormatTooNewError`) и просит обновить приложение. Локальные изменения этого файла остаются неотправленными.
- Неизвестные поля записей сохраняются при слиянии. Новые необязательные поля добавляются без повышения `v`.
- Порядок выкатки несовместимого формата описан в [DEPLOY.md](DEPLOY.md).

## 2. Слияние (CRDT)

Каждая запись — LWW-регистр (last-writer-wins):
1. побеждает запись с большим `updatedAt`;
2. при равенстве побеждает `deleted: true`;
3. при полном равенстве побеждает запись с лексикографически большей каноничной сериализацией.

Слияние коммутативно, ассоциативно и идемпотентно, поэтому все устройства сходятся к одному и тому же
состоянию независимо от порядка синхронизаций. Одинаковые теги, созданные на разных устройствах, сливаются
автоматически, потому что `id` тега равен его нормализованному имени.

## 3. Алгоритм синхронизации файла

```
loop (до 3 попыток):
  remote, version = GET file              # 404 → пусто, version = null
  merged = merge(local, remote)
  сохранить локально записи, которые изменились
  if merged ≠ remote:
     PUT file (If-Match: version | If-None-Match: *)
     412/409 → повторить цикл
  снять флаг «изменён локально»
```

Какие файлы синхронизируются: изменённые локально, изменённые на сервере (версия отличается от запомненной)
и отсутствующие на сервере.

## 4. API для режима «Регистрация»

Базовый URL: `CONFIG.REGISTRATION_API_URL`. Авторизация HTTP Basic: `client_id:client_secret`.
CORS: сервер должен разрешать `Authorization`, `Content-Type`, `If-Match`, `If-None-Match` и отдавать `Access-Control-Expose-Headers: ETag`.

### Регистрация

1. Клиент переходит на `REGISTRATION_URL?return_url=<URL приложения>&state=<случайная строка>`.
2. Сервис регистрирует пользователя/устройство и перенаправляет на
   `<return_url>?client_id=…&client_secret=…&state=<тот же state>`.
   Ошибка: `<return_url>?error=<код>&error_description=…&state=…`.
3. Клиент проверяет `state`, сохраняет учётные данные и удаляет их из адресной строки.

### Методы

| Метод | Путь            | Заголовки запроса                     | Ответ |
|-------|-----------------|---------------------------------------|-------|
| GET   | `/files`        |                                       | `200 {"files":[{"name":"day-2024-06-10.json","version":"<etag>"}]}` |
| GET   | `/files/{name}` |                                       | `200` тело файла, заголовок `ETag`; `404`, если файла нет |
| PUT   | `/files/{name}` | `If-Match: "<etag>"` или `If-None-Match: *` | `200/201` + `ETag`; `412`, если версия устарела |

- `{name}` соответствует `^(day-\d{4}-\d{2}-\d{2}|tags)\.json$`, максимальный размер 1 МБ.
- `401` означает неверные учётные данные: клиент показывает «нужен вход».
- Версия (ETag) должна меняться при каждой записи, например sha256 содержимого.

Эталонная реализация для разработки лежит в `tools/mock-api.php`.
